# Canvas size range expansion, 6×6 to 512×512, with custom sizing and presets

The original spec (`sprite-design-doc.md` §14, §20) deliberately closed off arbitrary canvas sizes, limiting new Files to a preset-only list and explicitly rejecting custom sizing: "No custom-size option — this was considered and deliberately dropped." This constraint was sound for the original scope — a minimalist pixel-art editor targeting small-scale rapid work — but later blocking three major features from the feature roadmap: palette extraction from image, reference image layers, and spritesheet import. All three are bounded by available canvas area. Raising the ceiling turns out to be less risky than building three features in ways that would impose artificial limits within a larger canvas, so it ships first as Plan A, prior to the feature additions themselves.

Decision: expand the canvas size range to 6×6 (minimum, well below the old 8×8) through 512×512 (maximum), permit non-square custom sizing with keyboard-friendly entry (Tab between width and height fields; `H` mirrors `W` until explicitly edited), and offer a preset menu with console/standard sizes. The presets are: **6×6, 9×9, 16×16, 24×24, 32×32, 64×64, Pico-8 (128×128), Game Boy DMG (160×144), 256×256, 512×512.** Choosing a preset also swaps the Project's active palette to match (Pico-8 swaps to Pico-8 palette, Game Boy DMG to DMG palette, others stay on the current palette). The minimum 6×6 supports the "micro-pixel editor" target; the maximum 512×512 holds because SVG export (which concatenates one `<rect>` per pixel, ~90 characters each) at that size produces roughly 23.6MB of markup, just under the 25MB warning gate at `export.js:143`. At 612² the result would be ~33.7MB, triggering the warning on every export.

Expanding the size range forces a rewrite of the pixel storage model. The current `model.pixels` is a plain `Array` of hex strings or `null`, which at 512² across a 24-frame, 4-layer File consumes roughly 288MB of pointer overhead. Replacement: a **Uint16Array of indices into a per-File color table** (not palette indices — a critical distinction, because `blendPixel` writes off-palette antialiased colors directly into the buffer, and this model must preserve that). Index 0 is reserved for transparent, replacing `null`. The palette's chips are a subset of the table; antialiased brush blends append new entries. Each File can hold 65,535 distinct colors (sufficient for any palette, all antialiased blends, and substantial headroom). This brings the 512² File down to roughly 72MB — a 4× reduction — making the size viable within a 4GB Chromebook's memory budget.

Typed buffers serialize as **raw binary, never as base64 inside JSON**. Base64 is 33% larger, and `JSON.stringify` over a large encoded string blocks the main thread on every autosave. IndexedDB stores `ArrayBuffer` natively with no encoding; the File System Access backend writes a binary sidecar `.sprite` file beside the project directory. This requires extending `storage.js` to support binary I/O alongside its current JSON-only path.

The `.sprite` file format advances to **v2**, indicated by adding `version: 2` to the File object; absence means v1. On load, v1 files auto-migrate: hex-string arrays convert to the color-table form and the File is re-saved as v2. Undo commands are dropped during migration (they're expensible state already cleared on every reopen), not converted. Existing projects gain this migration on first load with no separate step.

Storing typed buffers forced a second, deeper consequence: the memory footprint of undo itself. The current `commitLayerChange` (`main.js:701`) snapshots the entire `{layers, frames, activeLayerIndex}` state via `structuredClone` both before and after every structural edit (add/delete/reorder layer, add/delete/reorder frame), and `undo.js:14-29` replays whole state on undo. At 512² with 4 layers and 24 frames, this is fatal — one structural edit snapshots ~360MB of copied buffers, and the 50-step undo stack can hold multiple such snapshots. **Delta-based layer commands** replace whole-state recording: each command records only which layer changed and what its buffers became, not the entire project state. `applyLayerSnapshot` becomes a delta applier. This change is required for 512×512 to work at all and is a large memory win at every existing size.

Finally: every pan, zoom, and idle frame currently re-composites the entire visible canvas (the loop at `main.js:735`), even when nothing changed. At 512² this is a 262,144-pixel RGBA write per frame. Add a **composited-frame cache**, held in `file._compositeCache` (stripped from saves alongside the redo stack), invalidated whenever the canvas or any layer changes, then re-composited only on first access after invalidation. Dirty-rect tracking (record the changed bounding box per edit, re-walk only that region) is part of the same step — idle panning and zooming then cost one blit.

Together, these changes (v2 format, typed-array buffers, delta undo, composited cache) permit the 512×512 range to function responsively on low-end hardware while maintaining the performance-first design philosophy pinned in the project memory.
